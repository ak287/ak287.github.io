I didn't think of myself as a writer until I had to explain my code to someone who wasn't in the room.

That pull request comment. That README. That Slack message where I tried to describe, in plain English, why I'd made the architectural decision I had. Each one forced me to translate — to take something that existed only in my head and make it legible to another person.

That's writing. And it turns out developers do it constantly.

## The invisible craft

We tend to talk about writing as something separate from technical work. You code, or you write. But look at what a developer actually produces in a week:

- Commit messages
- Pull request descriptions
- Technical documentation
- Inline comments
- Architecture decision records
- Emails and Slack messages explaining technical concepts
- README files

All of it is writing. Most of it matters. Bad writing here means re-opened tickets, confused colleagues, and architectural decisions that nobody remembers the reasoning behind six months later.

## What coding and writing share

Both disciplines reward the same habits.

**Clarity over cleverness.** The clever solution that nobody else can follow is a liability. So is the sentence that makes you feel smart but confuses the reader. In both cases, the goal is communication.

**Cutting ruthlessly.** The best code is often the code you delete. The best paragraph is often the one you remove. When in doubt, cut.

**Revision is the work.** You don't write good prose in a first draft, and you don't write good code before you understand the problem fully. The first pass is just thinking out loud.

> "The first draft of anything is garbage." — Ernest Hemingway

He wasn't talking about pull requests, but he could have been.

## The practical upside

Developers who write well get promoted faster. Not because communication skills are valued over technical ones — they're not — but because writing is how technical work becomes visible.

If you can explain *why* a system works the way it does, not just *that* it works, you become someone people trust with bigger problems.

## Where to start

Write a README for something you've built. Not a great one — just an honest one. Explain what it does, why you built it, and how someone else would use it.

Then read it a week later and notice what's unclear.

That gap between what you meant and what you wrote — that's the work. Close it, one sentence at a time.
